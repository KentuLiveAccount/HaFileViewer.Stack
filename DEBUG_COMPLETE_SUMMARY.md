A comprehensive debug script has been created and executed to examine the empty lines bug in the viewport. The investigation has uncovered the **exact source and pattern of the bug**.

## Key Findings

### 1. The Bug Pattern

When viewport shows lines around 26-34:
- Line 26: len=23 (truncated - should be 243)
- Line 27: len=0 ← **EMPTY** (should be 223)
- Line 28: len=243 (correct)
- Line 29: len=0 ← **EMPTY** (should be 224)
- Line 30: len=223 (should be 243)
- Line 31: len=0 ← **EMPTY** (should be 242)
- Line 32: len=242 (should be 224)
- Line 33: len=0 ← **EMPTY** (should be 224)
- Line 34: len=224 (should be 223)

**Pattern**: Empty lines at odd positions (27, 29, 31, 33...)

### 2. Empty Lines Are NOT in the File

- Total lines in file: 71,356
- **No empty lines found in actual file**
- Lines 1-30 all have valid content when read correctly
- Empty lines are **GENERATED by the cache/viewport logic**

### 3. Cache Behavior

**When using getLinesFromStart (direct cache read):**
- All 30 lines are correct
- No empty lines
- All lengths match actual file content

**When using scrollDown (incremental cache read):**
- Every other new line is returned as empty
- Line numbers are correct (27, 29, 31, 33...)
- But content is empty or truncated
- Suggests **position/offset tracking bug**

### 4. Scroll-Up Bug

When scrolling back up from line 100:
- Successfully scrolls back through lines with empty line artifacts
- **Stops prematurely at line 15** (should reach line 1)
- Only scrolls up 61 times instead of expected ~75-76 times
- Indicates empty lines are **breaking the scroll-up logic**

## Root Cause

The bug appears to be in the **scrollDown operation's use of getLinesFrom**:

```haskell
(moreLines, topPos, bottomPos) <- getLinesFrom cache 
                                   (cursorBottomPosition cursor) 
                                   Forward 
                                   1 
                                   startLineNum
```

Issues:
1. **cursorBottomPosition is not accurate** after first read
2. **Line numbering calculation** (startLineNum) may be off
3. **Offset tracking** in the cache has a systematic error
4. Every second line requested gets wrong data

## Investigation Path

The bug occurs in one of these components:
1. **LineCache.getLinesFrom** - Returns wrong content/empty for certain positions
2. **BidirectionalScanner** - Boundary detection off by half a line
3. **ViewState cursor tracking** - Position not updated correctly
4. **Operations.scrollDown** - Logic error in how new lines are fetched/added
